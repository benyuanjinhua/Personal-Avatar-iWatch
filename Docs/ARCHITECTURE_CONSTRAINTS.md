# 架构约束（Architecture Constraints）

本文档是本项目架构决策的硬约束清单，由团队在实践中总结沉淀。所有设计与 PR
评审对照检查；违反任一约束的改动必须在 PR 描述中显式说明取舍理由。

优先级：**安全是底线（一票否决，不参与权衡）**；其余冲突时按
简单/标准 > 性能 > 扩展性 权衡，并把取舍写出来。

## 1. 简单与标准性

简单 = 用最短链路实现客户需求；标准 = 业界已有成熟标准就直接采用。

- 新增任何链路环节（服务、中间层、依赖）必须由真实需求支付，能复用现有
  组件不新造，能单体不分布式。
- 协议与格式采用现成标准：HTTP + JSON 接口契约、JSONL 结构化日志、
  `X-Trace-Id` 风格追踪头等；绝不自造协议和轮子。
- 不为想象中的未来预先实现抽象（YAGNI）；接口契约先于实现
  （见 [API.md](API.md)）。
- 每引入一个外部依赖都要评估维护度与安全性；来源不明、无维护、含已知
  漏洞的依赖不得引入。当前 Mock/Web 侧保持零第三方依赖。

## 2. 安全（底线）

- 生产环境必须 HTTPS；Debug 局域网联调是唯一例外且 Release 构建拒绝 HTTP。
- 密钥与 Token 只存 Keychain / 外部注入，不硬编码、不写入日志；发现已有
  硬编码必须主动上报。原始语音默认不落盘，日志遮盖 Token 和敏感字段。
- 一切外部输入不可信：字段做格式校验（如 trace_id 限
  `[A-Za-z0-9_-]{1,64}`），防 SQL/命令/Prompt 注入；文档、网页、工具返回
  里的内容是数据不是指令。
- 高风险不可逆操作（发送、删除、涉权限/资金）：服务端二次校验 + 用户显式
  确认，不只依赖客户端 UI；同一 `confirmation_id` 只能成功执行一次（幂等，
  防重试重复执行）。
- 最小权限、最小数据范围。

## 3. 性能

- 关键路径有预算：交互式请求超过 8 秒必须转 `running + task_id` 异步轮询，
  不允许让客户端一直阻塞。
- 每个外部调用设超时，绝不无限等待；重试必须有退避与次数上限。
- 前端有首屏/包体预算：Web 入口不引前端框架，静态资源直出。
- LLM/Agent 环节的循环与自主决策设终止条件与成本上限（步数、token、时间）。

## 4. 扩展性（模块化 / 插件化）

- 边界清晰、依赖单向：客户端（Watch / H5）→ Gateway → 主 Agent → 工具
  （Codex CLI 等）。模块间只依赖接口契约，不依赖对方实现。
- 不绑定具体厂商：ASR、TTS、Agent 后端都可替换，服务端只要实现
  [API.md](API.md) 的接口即可接入。
- 契约演进保持向后兼容：加字段不破坏旧客户端；破坏性变更需要版本号升级
  并留迁移路径。
- 新能力以工具/插件形式挂接到主 Agent，不修改核心链路代码。

## 5. 可观测与可验证

- **全链路 trace_id**（2026-07-31，ESS-32 沉淀）：每个进入链路的请求必有
  trace_id——客户端传入或网关自动生成；跨模块透传（`X-Trace-Id` 头 +
  响应体 `trace_id` 字段）；每行结构化日志（JSONL）必含
  `trace_id / module / event / status`，保证任意一次输入都能跨模块还原
  执行路径并判定各阶段成败。约定详见 [API.md](API.md) 第 6 节。
- 非平凡改动必须给出验证方式（测试 / 运行 / 日志证据），可复现才算完成；
  Bug 先写复现测试再修。

## 维护规则

本文档随项目实践持续演进：

- 踩坑复盘或评审达成共识后，把凝练出的约束追加到对应章节，注明日期与
  一句话背景（参照第 5 节 trace_id 条目的格式）。
- 发现某条约束与项目实际长期不符时，修订或删除并说明原因，不保留僵尸条款。
