# ESS-55 iWatch 语音对话交互体验重设计

状态：设计 + 首批实现已落地，待白梦林/PD 确认两项拍板问题（§8）。

设计原则（从三次补救反推）：**用户在任意时刻都必须知道「现在是什么状态、系统还欠我什么、我能做什么」**。手表上传达这件事的通道优先级：触觉 > 屏幕文字 > 语音。

## 2. 交互流程

以 issue 正文的 mermaid 流程图为准（含全部异常分支），本单实现与流程图节点的映射：

| 流程图节点 | 实现 |
|---|---|
| 抬腕/打开 App → 有未读结果 → 直接展示 + 触觉 | `WristAgentWatchApp` 冷启动与回前台调 `presentUnreadIfAny()`：触觉 `.notification`，有语音连播带看，纯文本直接全文 |
| 按住 → 触觉 + 波形 + 计时 | `pressBegan()` 播 `.start`；波形/电平已有 |
| 松手 <0.3s → 不发请求 | `pressEnded()` 拦截，`minimumRecordingMs = 300` |
| 提交 → 触觉成功 → 已收到 | `submit()` 播 `.success`；受理后 `.click`（状态族去重，见 §5） |
| 长任务 → 状态文字持续变化 | `WaitingStatusCopy` 阶梯 + 计秒，UI 每秒重算（§4） |
| 结果到达（前台/熄屏） | 事件层触发（`journal.onStateApplied`），不依赖 UI 挂载：触觉 `.notification` + 文字先渲染 + 语音跟播 |
| 失败 → 明确错误 + 一键重试 | 失败三型专属文案 + `retry(turn:)` 重发缓存录音，不用重新说 |
| 用户未响应 → 结果保留、下次打开仍未读 | `resultViewedAt` 持久化未读态（§6） |

## 3. 三条设计主张的正面回应

**主张 1（触觉是最强通道）——同意，已落地。** 全仓此前 0 处触觉调用，本单在 5 个关键节点落地（§5）。补充一条 HIG 约束：等待中间态（等手机/等 Mac/处理中）刻意**不**震——触觉的价值在于稀缺，节点间的进展交给屏幕文案。

**主张 2（>1s 有状态，>10s 有进展）——同意并加码为可测口径。** 每个等待相位阶梯文案（状态一变阶梯重置），阶梯走完后副标题计秒（「已等待 N 秒 · 完成会震动提醒」）。自动化测试钉死：**0–120s 内任意时刻 t，t 与 t+10s 的文案必不相同**（`WaitingStatusCopyTests`）。

**主张 3（文字先到眼睛，语音后到耳朵）——同意；现状核查 + 用例钉死。** 核查现状：`completed` 状态信封携带文字结果，入账即渲染；语音走 `transferFile` 后到，两者本就分链路。真机上「什么都没有」的成因更可能是结果信封整体未达（ESS-52 在查），而非 UI 等语音。本单做两件事防回归：① 自动化用例 `testTextSurvivesWhenSpeechPayloadIsDropped`——信封承诺了语音（speech_sha256 非空）但语音永远不到，文字仍完整在场且进入未读态；② 未读机制保证文字结果不因任何后续环节缺席而丢失。

## 4. 状态-文案对照表（全量，含异常）

等待态三列：0 秒起 / 阶梯推进（≤10s 必变）/ 长等尾部（每秒计数）。

| 状态 | 标题（0s 起） | 阶梯推进 | 长等尾部 | 触觉 |
|---|---|---|---|---|
| 录音中 | 我在听 | —（用户在主导） | — | 按下 `.start` |
| 录音太短 (<0.3s) | 没听清，请再按住说一次 | 不发请求 | — | `.failure` |
| 正在送出 | 正在送出 | 8s：还在送出…（录音不会丢） | 仍在送出 · 已等待 N 秒 | 提交 `.success` |
| 等待手机连接 | 等待手机连接（已排队，连上自动送出） | 10s：手机还没连上（确认 iPhone 在附近、蓝牙开启） | 仍在等手机 · 已等待 N 秒 | 无（见 §3 主张 1） |
| 已到手机，等待 Mac | 已到手机，等待 Mac（可以先放下手腕） | 10s：Mac 还没接单（确认 Mac 端助手在运行） | 仍在等 Mac · 已等待 N 秒 | 无 |
| 已受理 | 已收到，正在安排 | 8s：正在准备执行 | 排队中 · 已等待 N 秒 | `.click`（每回合一次） |
| 处理中（直答） | 已收到，正在思考 | 8s：还在想…（正在组织答案） | 快好了 · 已等待 N 秒 | 同上（状态族去重） |
| 处理中（长任务） | 已收到，正在处理（完成会震动提醒） | 10s：还在跑…（退出页面任务也会继续） | 仍在执行 · 已等待 N 秒 · 结果会保留 | 同上 |
| 需要确认 | 需要确认（未确认前不会执行） | 静态——等的是用户不是系统 | — | 无（本期；可议） |
| 完成 | 已完成 | 文字先渲染，语音跟播，字幕逐句高亮 | — | `.notification`（熄屏靠这下抬腕） |
| 失败：手机没连上 | 手机没连上 | 录音已保存，手机连上会自动重发；也可点「重试」 | — | `.failure` |
| 失败：Mac 没应答 | Mac 没应答 | 确认 Mac 端助手在运行，点「重试」不用重新说 | — | `.failure` |
| 失败：任务没能完成 | 任务没能完成 | 点「重试」再跑一次，不用重新说 | — | `.failure` |
| 语音丢失只有文字 | （直接展示全文视图） | 文字完整在场，进未读态 | — | `.notification`（completed 照常） |
| 结果过期 | 本期无过期机制 | 结果保留在时间线（上限 20 条，旧的滚出） | — | — |

「执行失败」及一切用户看不懂的兜底文案已从代码中移除。

## 5. 触觉映射（5 个关键节点）

| 节点 | cue | WKHapticType | 触发源 | 去重 |
|---|---|---|---|---|
| 按下开始录音 | recordingStarted | `.start` | `pressBegan()` 本地 | 手势天然一次 |
| 松手提交成功 | requestSubmitted | `.success` | `submit()` 本地 | 一次 |
| 任务被受理 | taskAccepted | `.click` | 状态入账事件 | 受理状态族（accepted/processing 等）每回合一次，允许跳态 |
| 结果到达 | resultArrived | `.notification` | 状态入账事件 | 每回合一次 |
| 失败 | turnFailed | `.failure` | 状态入账事件 | 每回合一次 |

关键实现决策：远端三类 cue 挂在**状态入账事件**（`VoiceTurnJournal.onStateApplied`）而不是 UI 上——熄屏/视图未挂载时结果到达仍触发触觉。前提是 App 还在运行：ESS-45 的 ExtendedRuntimeSession 覆盖回合期间（≤10 分钟，见 §8.2 缺口）。

## 6. 未读结果机制

- **到达 ≠ 已读**。已读的判定必须是用户可证实的行为：① 用户关闭全文视图（主动 dismiss）；② 完整听完结果语音（熄屏听完也算送达）；③ 主动点开「查看全文」后关闭。
- 未读态持久化（`resultViewedAt`，随回合日志落盘），App 杀掉重开仍在。
- 打开 App / 回前台时若有未读：触觉提醒 + 直接呈现（有语音连播带看，纯文本直接全文），欢迎语让路。

## 8. 待白梦林拍板（附建议）

1. **触觉默认全开还是可配置？** 建议：**默认全开、本期不加配置项**。理由：手表用户对触觉容忍度高；5 节点 + 去重已把频率压到每回合最多 4 次；加配置 = 复杂度 + 测试面翻倍。若 10 分钟真机验收反馈「吵」，再收敛为「仅结果/失败」。
2. **结果到达是否发系统通知？** 建议：**本期不发，但下一单要做**。本期靠「触觉 + 未读机制」兜底；已知缺口：ExtendedRuntimeSession 上限 ~10 分钟，超长任务结果回来时若 App 已被挂起，触觉发不出来，此时**本地通知是唯一可靠回访通道**（HIG 同款结论）。是否命中该缺口取决于真实任务时长分布，建议拿真机数据后单独立单。
